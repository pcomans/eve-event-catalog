## Gate rationale

- Terminality is correct. `node_modules/eve/dist/src/protocol/message.d.ts:478-503` defines `session.waiting` as parked, `session.failed` as failed, and `session.completed` as completed. `node_modules/eve/dist/src/harness/emission.js` emits `session.waiting` from `emitRecoverableFailedTurn` and conversation-mode `emitTurnEpilogue`, `session.completed` from task-mode `emitTurnEpilogue`, and `session.failed` from `emitFailedStep`. `node_modules/eve/dist/src/harness/tool-loop.js` uses those helpers consistently for successful, recoverable, and unrecoverable paths. Eve's own `openStreamIterable` reconnects only after a disconnect error and returns on clean EOF. No other top-level protocol event is terminal; child terminal events are wrapped as `subagent.event` and therefore cannot falsely retire the parent transcript.

- Exceptional marker-less endings exist, so continuing at the cap is the right trade. In the minified `node_modules/eve/dist/src/execution/workflow-entry.js:1`, `waitForNextDeliver()` can return `null` if the delivery hook ends, and the minified `node_modules/eve/dist/src/execution/workflow-steps.js:1` explicitly catches and logs failure to write a terminal `session.failed` marker. These paths can close a genuinely finished durable stream without an in-band marker. The policy then runs 2s, 4s, 8s, 16s, 32s, 60s, and remains at 60s (about 120 proxied function invocations/hour/tab for immediate failures). Retiring instead would make an indistinguishable wifi outage, deployment interruption, or proxy failure permanently freeze a still-live transcript. Visibility gating removes subsequent retries while hidden.

- The health reset is appropriate for the current cursorless stream. A short full-history replay sets `published` but fails the 30-second duration test, so the incident shape cannot rebuild a fixed 2-second loop. A long empty stall fails the delivery test. Because every current reconnect starts at index 0, a genuinely live session normally replays at least `session.started`/history and then remains held open; duration plus delivery is the best available signal. A connection that replays old history and then stalls for 30 seconds can reset the ladder, but its own 30-second hold already bounds request frequency and it cannot reproduce the measured sub-second storm.

- Retirement cannot be resurrected. `observatory/lib/poll-loop.ts:93-97` sets the one-way `stopped` flag, cancels the pending timer, and unsubscribes visibility. A queued visibility callback reaches `tick()`, which returns at `:101`; a late in-flight completion can consult the interval getter but cannot schedule because `:112` checks `!stopped`. Repeated `retire()`/cleanup calls are idempotent for browser timers and event listeners.

- The untested hook wiring is ordered correctly. In `observatory/lib/use-session-transcript.ts:260-272`, every non-cancelled outcome assigns `nextDelayMs` before the awaited run resolves and before `startPollLoop` consults its getter: terminal assigns `null`, every nonterminal outcome assigns the policy delay. The sole unassigned return is the cancelled path at `:260`; effect cleanup synchronously sets `cancelled`, aborts the request, and calls `stop()` at `:275-278`, so the late completion cannot schedule. React Strict Mode's setup/cleanup replay has the same safe ordering.

- `usePolling` preserves its request, abort, cancellation, state, and loading semantics. It still starts immediately when visible, keeps one request in flight, clears errors only on success, leaves prior data intact on failure, sets loading false after the first settled request, suppresses post-unmount state writes, and aborts the shared request signal. Its intended behavior change is that hidden tabs hold no retry timer and refresh immediately on visibility return.

- The tests discriminate the intended unit behavior: both terminal markers, nonterminal `session.waiting`, marker-less EOF, late read failure after a terminal marker, the complete capped ladder, cap flooring, both halves of the health predicate, null retirement across visibility changes, in-flight visibility races, and cleanup are asserted. On `main`, the new tests cannot even import the extracted APIs, and the old unconditional reconnect has no terminal outcome to satisfy them. Git history adds tests and implementation in the same commit, so test-first execution order cannot be independently proven from commits, but the resulting red/green boundary is substantive rather than tautological. The acknowledged React-effect integration seam remains untested; the line-by-line ordering audit above found no defect.
